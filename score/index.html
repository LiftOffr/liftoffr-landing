Corrected 20 Aug 2026

This number went up today because I fixed a bug in my own code, and you should know what it was. When the data source publishes no reading for one of the nine on a given day, my code was treating that gap as a reading of zero and averaging it in, instead of leaving it out. Today that understated the Score by 1.8 points — it read 34.5 when it should have read 36.3. Anyone who pulled the data and recomputed it properly would have got a different number from mine and would have been right. A missing reading is now excluded and the divisor drops to match, which is what the table above shows. The 64-signal record at /receipts is unaffected — it was generated by a separate script that always handled gaps correctly.

Two things worth saying plainly: CBBI is the data source these readings are pulled from, not a component, and the Score contains no Fear & Greed and no Google Trends. I wrote about both for a long time; neither carries any weight in the number.

Recompute it yourself

  1. Pull CBBI's public daily data. It is free and needs no account.
  2. Take today's value for each of the nine components above and scale it to 0–100.
  3. Multiply each by its weight, add them together, then divide by the weights you actually used — that is 1.00 on a normal day, and less if CBBI published no reading for one of the nine. A missing reading is left out, never counted as a zero.
  4. You should land on the number at the top of this page.

Want to check my working rather than your own? /api/cycle-score returns every component, its weight and its reading as JSON. Open it. An outside auditor ran this in August 2026 and got 34.35 against a published 34.4 — the gap is rounding.

If you run it and get a materially different number, tell me and I will fix it. That offer is the entire reason the weights are public.
